В предыдущих главах мы построили все компоненты по отдельности: skip list как memtable, SSTable для хранения на диске,
WAL для durability. Пришло время собрать их в единый LSM Engine — и добавить два фоновых процесса, без которых
хранилище не будет работать: сброс (flush) и compaction.

Напоминаю, что такое LSM-tree — мы подробно разбирали его в [главе 1.4]({% post_url 2026-05-02-part-1.4 %}).
LSM-tree (Log-Structured Merge Tree) — это архитектурный паттерн для storage engine, в котором все записи
буферизируются в памяти (memtable) и периодически сбрасываются на диск как отсортированные иммутабельные файлы
(SSTable). Устаревшие версии данных удаляются через фоновый процесс compaction. Три компонента —
memtable, SSTable и WAL — работают вместе именно по этой схеме.

## Из чего состоит LSM Tree

LSM Tree — это не один файл и не одна структура в памяти. Это набор файлов в директории на диске, плюс структуры
в оперативной памяти, которые работают вместе как единое хранилище. Если заглянуть в рабочую директорию LSM Engine,
вы увидите примерно такую картину:

```
  /var/data/mydb/
  ├── MANIFEST        ← метаинформация: какие SST файлы, на каких уровнях
  ├── wal-0001.log    ← журнал операций (WAL)
  ├── wal-0002.log    ← следующий WAL (после ротации)
  ├── sst-0001.dat    ← SSTable файлы
  ├── sst-0002.dat
  ├── sst-0003.dat
  └── ...
```

Четыре компонента — и каждый решает свою задачу:

### WAL (Write-Ahead Log)

Файл (или несколько файлов после ротации), в который записываются все операции перед тем, как попасть в память.
Последовательный append — самый быстрый способ писать на диск. Если процесс упадёт, WAL используется для
восстановления: при следующем старте все записи из WAL повторно применяются в memtable. Без WAL данные,
которые ещё не успели сброситься на диск в виде SSTable, были бы потеряны.

### SkipList (MemTable)

Активная in-memory структура, которая принимает все новые записи. SkipList выбран не случайно: он поддерживает
упорядоченные вставки и поиск за O(log n), а итерация по нему выдаёт ключи в отсортированном порядке —
это критически важно для сброса на диск. Когда memtable заполняется (по умолчанию — 64 МБ), она «замораживается» —
становится immutable — и переносится в очередь на сброс. На её место создаётся новая пустая memtable
с новым WAL файлом.

### SSTable (Sorted String Table)

Иммутабельные файлы, в которых хранятся отсортированные ключи и значения. SSTable никогда не модифицируется
после создания — только читается. Файлы организованы по уровням: L0, L1, L2 и далее. На L0 файлы могут
пересекаться по ключам (каждый сброс создаёт независимый файл). На L1 и ниже файлы не пересекаются —
каждый ключ принадлежит ровно одному SSTable на уровне. Каждый следующий уровень примерно в 10 раз больше
предыдущего.

### Manifest

JSON-файл, который хранит текущее состояние LSM на диске: какие SST файлы существуют, на каком уровне
и в каком порядке. Обновляется атомарно — сначала запись во временный файл, потом `rename`. Это гарантирует,
что manifest всегда консистентен, даже если процесс упадёт посередине записи. Без manifest при рестарте engine
не смог бы восстановить структуру уровней.

## Три операции: Put, Delete, Get

### Put — запись

Каждая операция Put проходит через два этапа:

```
  Put("user:42", "alice")

  Шаг 1: WAL (диск)
  ┌──────────────────────────────────────────┐
  │  WAL: [...] [PUT user:42 → alice]        │
  │                                ▲         │
  │                       append + fsync     │
  └──────────────────────────────────────────┘

  Шаг 2: MemTable (память)
  ┌──────────────────────────────────────────┐
  │  SkipList:                               │
  │    config   → ...                        │
  │    user:42  → alice  ← вставили          │
  └──────────────────────────────────────────┘

  ◄── ok
```

Порядок важен: сначала WAL, потом memtable. Если процесс упадёт между шагами — данные в WAL будут
восстановлены при следующем старте. Промежуточного состояния «данные в памяти, но не на диске» нет.

### Delete — удаление

Delete работает как Put, но вместо значения записывает tombstone — специальную запись со значением `nil`. Физически
данные не удаляются: tombstone просто перекрывает предыдущее значение при чтении. Реальное удаление происходит
позже, при compaction, когда tombstone сливается с более старыми версиями и убирается, если на более глубоких
уровнях нет устаревших данных.

### Get — чтение

Чтение устроено сложнее записи. Нужно проверить несколько мест в определённом порядке — от самых свежих данных к старым:

```
  Get("user:42")

  1. MemTable (память)       ← самые свежие данные
     │ Нашли? → возвращаем
     │ Не нашли ↓

  2. SSTable на диске (от новых к старым)
     │ Нашли? → возвращаем
     │ Не нашли ↓

  3. ErrNotFound
```

Сначала ищем в памяти — это быстро. Если не нашли — идём на диск и проверяем SSTable файлы от самых свежих к старым.
Если ключ найден, возвращаем его. Если проверили все SSTable и ничего — `ErrNotFound`.

## Почему одного WAL, memtable и SSTable недостаточно

Вот что мы имеем на данный момент: LSM Tree записывает данные в WAL и memtable, а при чтении ищет сначала
в memtable, потом в SSTable. Простая и понятная схема.

Но есть вопрос — в какой момент данные попадают в SSTable? И что будет, если WAL, memtable и SSTable
будут расти вечно?

### Проблемы

**1. Память.** Memtable живёт в оперативной памяти. Если мы будем бесконечно записывать в одну memtable —
она рано или поздно заполнит всю RAM. RAM конечна, а memtable растёт с каждой записью.

```
  Без ограничения:

  MemTable: [key1] [key2] [key3] ... [key1000000] ← заполняет всю RAM
  WAL:      ... 10 ГБ appended ...                ← заполняет весь диск
  SSTable:  ... 50 ГБ одной кучей ...             ← невозможно эффективно читать
```

**2. Чтение.** Один SSTable файл размером 50 ГБ — это бесполезно. Приходится сканировать огромный файл
для каждого Get. SSTable нужно разбивать на файлы, чтобы можно было быстро найти нужный ключ и не читать лишнего.

**3. Мёртвые данные.** Каждый Set перезаписывает предыдущее значение. Каждый Delete добавляет tombstone.
Старые версии и tombstone физически остаются в файлах и занимают место. Если никогда не очищать —
диск заполнится данными, которые уже никто не читает.

```
  SSTable после 1000 обновлений ключа "hotkey":

  hotkey=v1, hotkey=v2, hotkey=v3, ... hotkey=v999
  ↑ актуально только последнее значение, остальные — мусор
```

### Решение: несколько WAL, несколько memtable, несколько SSTable

Чтобы справиться со всеми тремя проблемами, LSM Tree использует не один файл каждого типа, а множество:

- **Несколько WAL.** Каждый WAL привязан к своей memtable. Когда memtable сбрасывается на диск —
  старый WAL больше не нужен и может быть удалён.
- **Несколько memtable.** Активная memtable принимает новые записи. Когда она заполняется — замораживается
  (становится immutable) и переносится в очередь на сброс. На её место создаётся новая пустая memtable.
  Пока immutable memtable ждёт сброса, клиент продолжает работать с новой — без блокировок.
- **Несколько SSTable.** Каждый сброс создаёт новый SSTable файл. Файлы организованы по уровням:
  L0, L1, L2 и далее. Compaction — фоновый процесс, который сливает SSTable между уровнями и удаляет
  мёртвые данные.

```
  Память:

  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │  MemTable    │   │  Immutable   │   │  Immutable   │
  │  (активная)  │   │  #1 (ждёт    │   │  #2 (ждёт    │
  │              │   │   сброса)    │   │   сброса)    │
  └──────┬───────┘   └──────────────┘   └──────────────┘
         │
    WAL (активный)

  Диск:

  ┌─────────────────────────────────────────┐
  │ L0: [SST] [SST] [SST]                   │  ← из сбросов
  │─────────────────────────────────────────│
  │ L1: [SST] [SST] [SST] [SST]             │  ← после compaction
  │─────────────────────────────────────────│
  │ L2: [SST] [SST] [SST] [SST] [SST]       │
  └─────────────────────────────────────────┘
```

## Manifest, уровни SSTable и жизненный цикл WAL

Чтобы решить три проблемы (память, чтение, мёртвые данные), LSM Tree использует не один файл каждого типа,
а множество. Разберём каждый механизм отдельно.

### Несколько memtable и WAL

Memtable живёт в памяти. RAM конечна — значит, memtable не может расти вечно. Решение: когда memtable
заполняется (по умолчанию — 64 МБ), она замораживается и становится immutable. На её место создаётся
новая пустая memtable. Клиент продолжает писать в новую — без блокировок.

```
  MemTable заполнилась (64 МБ)
  │
  ├─ 1. Текущая memTable → immutable (замораживаем)
  │
  ├─ 2. Создаём новую пустую memTable
  │
  └─ 3. Клиент продолжает работу — записи идут в новую memTable
```

Но если memtable заморожена — её нужно куда-то сбросить. Фоновый процесс flush делает это: берёт immutable
memtable и записывает все её ключи и значения в SSTable файл на диске. Данные в memtable уже отсортированы
(это SkipList), поэтому запись на диск — один sequential pass.

Теперь про WAL. WAL нужен для crash recovery — чтобы восстановить данные, которые ещё не попали в SSTable.
Если WAL один на все memtable, возникает проблема: старые memtable уже сброшены в SSTable, а новые — ещё нет.
Нельзя удалить часть WAL, не потеряв данные. Поэтому каждый WAL привязан к своей memtable — один к одному:

```
  WAL #1 ──► MemTable (активная)
                  │
                  │ заполнилась (64 МБ)
                  ▼
  WAL #1 ──► MemTable (заморожена, immutable)
  WAL #2 ──► MemTable (новая, активная)
                  │
                  │ flush в фоне
                  ▼
  SST-001.dat    ← данные из MemTable #1
  WAL #1         ← можно удалить, данные уже в SSTable
```

Последовательность:

1. Активная memtable заполняется. Все записи идут в связанный с ней WAL.
2. Memtable замораживается — становится immutable. Создаётся новая пустая memtable с новым WAL.
3. Фоновый процесс flush сбрасывает immutable memtable в SSTable на L0.
4. Старый WAL больше не нужен — удаляется.

### Уровни SSTable (leveled compaction)

Каждый сброс создаёт новый SSTable файл. Если файлы accumulate без организации — чтение замедляется:
приходится проверять bloom filter каждого файла. Поэтому SSTable организованы в уровни — иерархию,
где каждый следующий уровень крупнее предыдущего.

**L0** — файлы из сброса memtable. Каждый сброс создаёт независимый SSTable. Файлы на L0 могут
пересекаться по ключам, потому что каждый сброс — это слот памяти со своим набором ключей:

```
  Сброс #1 (memtable содержала a, b, c, d, e, f):
    SST: [a-f]

  Сброс #2 (memtable содержала c, d, e, f, g, h, i, j, k):
    SST: [c-k]

  Оба файла на L0, оба содержат ключи c, d, e, f — пересечение!
```

**L1+** — файлы не пересекаются по ключам. Каждый ключ принадлежит ровно одному SSTable на уровне.
Это результат работы compaction — фонового процесса, который сливает файлы с верхнего уровня
на нижний и оставляет только актуальные версии. Каждый следующий уровень примерно в 10 раз
больше предыдущего по размеру.

```
  L0:  [a-f] [c-k] [g-p]     ← файлы пересекаются по ключам
  │
  ▼ compaction
  L1:  [a-d] [e-h] [i-m] [n-p]   ← файлы не пересекаются
  │
  ▼ compaction
  L2:  [a-c] [d-g] [h-k] [l-m] [n-p]   ← ещё больше, но упорядочены
```

Зачем уровни, а не плоский список? При чтении нужно проверять как можно меньше файлов. С уровнями:
сначала L0 (обычно 4-8 файлов), затем один файл на L1 (бинарный поиск), затем один файл на L2.
На каждом уровне ключ принадлежит максимум одному файлу — это позволяет быстро отсечь лишнее.

### Manifest

Теперь у нас есть несколько WAL, несколько memtable (активная + immutable) и SSTable файлы на разных
уровнях. Как engine понимает, что где лежит? Какие SSTable актуальны, а какие уже удалены
после compaction? Какой WAL привязан к какой memtable? Без дополнительной информации файлы на диске —
просто набор бинарных данных без контекста.

Для этого существует **manifest** — JSON-файл, который хранит полное состояние LSM Tree:

```go
type Manifest struct {
    Levels      [][]string `json:"levels"`        // levels[i] = список имён SST файлов
    NextFileNum uint64     `json:"next_file_num"` // следующий свободный номер файла
    // Номера WAL-файлов, чьи memtables ещё не flush'нуты на диск.
    // При recovery replay'им все эти WAL от старого к новому.
    WALFileNums []uint64 `json:"wal_file_nums"`
}
```

Обратите внимание: в manifest хранятся **все WAL файлы**, чьи memtable ещё не сброшены в SSTable.
Не только активный, но и WAL от immutable memtable, которые ждут своей очереди на flush. После flush
самый старый WAL удаляется с диска и убирается из manifest. Так при рестарте engine точно знает,
какие WAL нужно replay'ить.

```
  Manifest:

  {
    "levels": [
      ["000001-l0.sst", "000003-l0.sst", "000006-l0.sst"],         ← L0
      ["000004-l1.sst", "000005-l1.sst", "000007-l1.sst"]          ← L1
    ],
    "next_file_num": 8,
    "wal_file_nums": [2, 5, 7]
  }

  wal_file_nums: [2, 5, 7]
                  │  │  │
                  │  │  └─ 000007.wal → активный WAL (последний в списке)
                  │  └──── 000005.wal → immutable memtable #2
                  └─────── 000002.wal → immutable memtable #1 (самая старая)
```

Восстановление при рестарте:

1. Загружаем manifest — узнаём SSTable файлы по уровням и список WAL.
2. Открываем все SSTable файлы, записанные в manifest.
3. Replay'им WAL от старого к новому: каждый WAL восстанавливает свою memtable.
   Старые WAL — их memtable идут в immutables, последний WAL — становится активной memtable.
4. Запускаем фоновые горутины flush и compaction.

Почему manifest хранит несколько WAL, а не один активный? Потому что между моментом заморозки
memtable и моментом flush может пройти время — immutable memtable ждёт своей очереди. Если в этот
момент процесс упадёт, данные из immutable memtable нужно восстановить. А для этого нужен её WAL.
Старый WAL нельзя удалить до завершения flush — и manifest должен знать о его существовании.

При каждом изменении структуры SSTable (сброс, compaction) — manifest обновляется. Обновление атомарное:
сначала запись во временный файл, потом `rename`. Это гарантирует, что manifest всегда консистентен,
даже если процесс упал посередине записи.

## Как всё работает вместе

Теперь у нас есть все куски пазла. Давайте посмотрим, как LSM Tree ведёт себя при реальной нагрузке —
от первой записи до compaction.

### Запись: Put("user:42", "alice")

```
  Put("user:42", "alice")

  1. WAL (диск)
  ┌──────────────────────────────────────────┐
  │  000001.wal: [...] [PUT user:42 → alice] │
  │                                ▲         │
  │                       append + fsync     │
  └──────────────────────────────────────────┘

  2. MemTable (память)
  ┌──────────────────────────────────────────┐
  │  SkipList:                               │
  │    user:42  → alice  ← вставили          │
  └──────────────────────────────────────────┘

  ◄── ok
```

Запись идёт в WAL и memtable. Manifest хранит `wal_file_nums: [1]` — один активный WAL.

### Memtable заполнилась

Клиент продолжает писать. Eventually memtable достигает 64 МБ. В этот момент:

```
  MemTable.byteSize >= 64 МБ
  │
  ├─ 1. Текущая memTable → immutable (замораживаем)
  │
  ├─ 2. Создаём новую пустую memTable + новый WAL (000002.wal)
  │
  └─ 3. Сигнал в flushCh — фоновый flush начнётся

  Manifest: wal_file_nums: [1, 2]
                              │  │
                              │  └─ активный WAL
                              └──── immutable memtable (ждёт flush)
```

Клиент продолжает работать — записи идут в новую memtable через новый WAL. Immutable memtable
ждёт flush в фоне. Два WAL в manifest — оба нужны для crash recovery.

### Flush: immutable memtable → SSTable (L0)

Фоновый процесс flush берёт самую старую immutable memtable и записывает её в SSTable на L0:

```
  flushOldestImmutable()

  1. Lock: берём самую старую immutable
  2. Unlock
  3. Итерируем memtable → записываем все KV в SST
     (данные уже отсортированы — один sequential pass)
  4. writer.Finish() → flush + fsync
  5. Lock:
     ├── levels[0] = append(levels[0], newSST)
     ├── immutables = immutables[:len-1]
     ├── walNums = walNums[1:]  (убираем старый WAL)
     └── удаляем 000001.wal с диска
  6. Unlock
  7. saveManifest()

  Manifest: wal_file_nums: [2]    ← старый WAL удалён
  L0: [000003-l0.sst]             ← новые данные на диске
```

Flush — быстрая операция: данные в memtable уже отсортированы, запись на диск — один sequential pass.
Но чем чаще мы сбрасываем, тем больше SST файлов накапливается на L0. А чем больше файлов на L0 —
тем медленнее чтение, потому что нужно проверять bloom filter каждого файла.

### Compaction: L0 → L1

Когда на L0 накапливается 4 SSTable файла — запускается compaction. Compaction берёт файл с L0,
находит пересекающиеся файлы на L1 и делает merge sort:

```
  До compaction:

  L0:  [a-f] [c-k] [g-p] [m-z]   ← файлы пересекаются!
        │
        ▼ выбираем victim: [a-f]

  L1:  [a-d] [e-h] [i-m] [n-r] [s-z]
        │     │
        ▼     ▼
      overlapping: [a-d] и [e-h]

  Merge sort: victim [a-f] + overlapping [a-d], [e-h]
    │
    ▼ для каждого ключа — только самая свежая версия
    ▼ tombstone на последнем уровне — удаляем

  После compaction:

  L0:  [c-k] [g-p] [m-z]         ← убрали victim
  L1:  [a-d'] [e-h'] [i-m] [n-r] [s-z]
        ▲      ▲
        новые SST файлы (остальные не тронули)
```

Compaction решает три проблемы одновременно: уменьшает количество файлов на L0 (быстрее чтение),
удаляет мёртвые данные (старые версии и tombstone) и поддерживает уровни упорядоченными.

### Чтение: Get("user:42")

Теперь, когда у нас есть все компоненты, чтение проверяет несколько мест от свежих к старым:

```
  Get("user:42")

  1. Активная MemTable          ← самые свежие данные
     │ Нашли? → возвращаем
     │ Не нашли ↓

  2. Immutables (от новых к старым)
     │ Нашли? → возвращаем
     │ Не нашли ↓

  3. L0: все SST от новых к старым (файлы могут пересекаться по ключам)
     │ Нашли? → возвращаем
     │ Не нашли ↓

  4. L1, L2, ... — бинарный поиск по ключевому диапазону (нет пересечений)

  5. ErrNotFound
```

На L1 и ниже файлы не пересекаются по ключам — достаточно бинарного поиска. На L0 файлы из разных
сбросов могут содержать одни и те же ключи, поэтому проверяем каждый.

### Визуально: полная картина

```
                          ┌─────────────────────────────────────────────────┐
                          │                  LSM Engine                     │
                          │                                                 │
     Put(k,v) ──────────────►  ┌─────────┐      ┌──────────────┐            │
     Delete(k) ─────────────►  │   WAL   │─────►│   MemTable   │            │
                               │  (диск) │      │  (SkipList)  │            │
                               └─────────┘      └──────┬───────┘            │
                                                       │ byteSize >= 64 МБ  │
                                                       ▼                    │
                                                  ┌──────────────┐          │
                                                  │  Immutables  │          │
                                                  │  [0] [1] ... │          │
                                                  └──────┬───────┘          │
                                            flush         │                 │
                                          (background)    ▼                 │
                                ┌───────────────────────────────────────┐   │
                                │ L0: [SST] [SST] [SST] [SST]           │   │
                                │     файлы могут пересекаться по ключам│   │
                                │───────────────────────────────────────│   │
                                │ L1: [SST] [SST] [SST]                 │   │
                                │     отсортированы, без пересечений    │   │
                                │───────────────────────────────────────│   │
                                │ L2: [SST] [SST] [SST] [SST] [SST]     │   │
                                │     отсортированы, ~10x больше L1     │   │
                                └───────────────────────────────────────┘   │
                                     compaction (background)                │
                                        L(n) merge → L(n+1)                 │
                          └─────────────────────────────────────────────────┘
```

Три фоновых процесса работают параллельно: main goroutine обрабатывает Set/Get/Delete, flushWorker
сбрасывает замороженные memtable в SST, compactWorker сливает SST между уровнями. Manifest обновляется
при каждом изменении структуры — и при рестарте engine точно знает, что где лежит.

type Manifest struct {
    Levels      [][]string `json:"levels"`        // levels[i] = список имён SST файлов

func (e *LSMEngine) saveManifest() error {
    m := Manifest{
        NextFileNum: e.nextFileNum.Load(),
        WALFileNums: e.walFileNums(),
    }
    for _, level := range e.levels {
        var names []string
        for _, sst := range level {
            names = append(names, sst.path)
        }
        m.Levels = append(m.Levels, names)
    }
    data, _ := json.Marshal(m)
    // Атомарная запись: сначала во временный файл, потом rename:
    tmp := filepath.Join(e.dir, "MANIFEST.tmp")
    if err := os.WriteFile(tmp, data, 0644); err != nil {
        return err
    }
    return os.Rename(tmp, filepath.Join(e.dir, "MANIFEST"))
}

func loadManifest(dir string) (*Manifest, error) {
    data, err := os.ReadFile(filepath.Join(dir, "MANIFEST"))
    if os.IsNotExist(err) {
        return &Manifest{}, nil // первый запуск
    }
    if err != nil {
        return nil, err
    }
    var m Manifest
    return &m, json.Unmarshal(data, &m)
}

### Merging Iterator

Compaction делает merge sort нескольких SST файлов. Для этого нужен `mergingIterator` —
k-way merge поверх отсортированных итераторов. На каждом шаге выбирает итератор с наименьшим ключом.

```go
// storage/merging_iterator.go

type mergingIterator struct {
	iters   []Iterator
	current int  // индекс итератора с минимальным ключом, -1 если исчерпаны
	started bool // false до первого вызова Next
}

func newMergingIterator(iters []Iterator) *mergingIterator {
	m := &mergingIterator{iters: iters, current: -1}
	m.findSmallest()
	return m
}

func (m *mergingIterator) findSmallest() {
	m.current = -1
	for i, it := range m.iters {
		if !it.Valid() {
			continue
		}
		if m.current == -1 || bytes.Compare(it.Key(), m.iters[m.current].Key()) < 0 {
			m.current = i
		}
	}
}

func (m *mergingIterator) Next() bool {
	if !m.started {
		m.started = true
		return m.current >= 0
	}
	if m.current < 0 {
		return false
	}
	m.iters[m.current].Next()
	m.findSmallest()
	return m.current >= 0
}

func (m *mergingIterator) Valid() bool  { return m.current >= 0 }
func (m *mergingIterator) Key() []byte  { return m.iters[m.current].Key() }
func (m *mergingIterator) Value() []byte { return m.iters[m.current].Value() }
```

Простая реализация с линейным поиском минимума — O(k) на Next. Для leveled compaction с 2-10 итераторами
это достаточно быстро (LevelDB использует тот же подход). Для десятков итераторов можно заменить на min-heap
через `container/heap` — O(log k) на Next.

Важно: дедупликация ключей не в итераторе, а в вызывающем коде `compactLevel` —
`if bytes.Equal(k, prevKey) { continue }`. Итератор честно выдаёт все ключи из всех источников
в отсортированном порядке, включая дубликаты.

## Плюсы

- **Высокая пропускная способность на запись.** Sequential WAL append + in-memory insert. Compaction работает в фоне и не блокирует запись (кроме критических моментов).
- **Данные больше RAM.** MemTable — это буфер. Основное хранилище — SSTable на диске. Можно хранить терабайты.
- **Range scan.** Данные отсортированы и в memtable, и в SSTable. Bloom filter + index block — эффективный поиск.
- **Crash recovery.** WAL гарантирует durability. Manifest — консистентное восстановление структуры levels.

## Минусы

- **Read amplification.** В худшем случае чтение проверяет memtable + все immutable + все SST на L0 + по одному SST на каждом уровне. Bloom filter помогает, но не устраняет проблему полностью.
- **Write amplification.** Каждая запись проходит через WAL, сброс и несколько уровней compaction. Реально записанных на диск данных может быть в 10-30 раз больше, чем написал клиент.
- **Всплески латентности.** Compaction конкурирует с пользовательскими операциями за CPU и I/O. Write stall — известная проблема, когда L0 заполняется быстрее, чем compaction успевает обработать.
- **Сложность.** Сброс, compaction, manifest, graceful shutdown, конкурентность — это уже существенно сложнее, чем всё, что мы писали раньше.
